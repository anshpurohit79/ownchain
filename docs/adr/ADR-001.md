# ADR-001 — Remove Orchard transfers, shielded coinbase and all Orchard pool accounting from v1

**Status:** SUPERSEDED by ADR-004 — Shielded-First Hybrid Architecture (Experimental-v1 baseline)
**Identifier:** ADR-001
**Date:** 2026-10-29
**Author:** OwnChain protocol decision phase
**Depends on:** none
**Supersedes:** none

**Superseded by:** ADR-004 — Shielded-First Hybrid Architecture

---

## 1. Context

OwnChain protocol v1 (`docs/protocol-v1.md`) previously specified shielded-only ordinary transfers and a shielded coinbase using Orchard V2:

- Ordinary transfers required Orchard V2 proofs, actions, nullifiers, and commitment tree anchors.
- Spendable value was tracked in an opaque shielded pool via `valueBalanceOrchard`.
- Genesis committed the empty Orchard commitment tree root.
- The block header committed to `orchard_commitment_root` in a 32-byte slot.

However, an experimental network requiring account-level governance mechanisms—specifically spend allowances, replay nonces, delayed withdrawals, freeze/recovery, guardian multi-signature quorums, and coinbase maturity tracking (see ADR-002)—cannot express these mechanics inside shielded notes without custom zero-knowledge circuits. Custom circuits are explicitly excluded by OwnChain v1 non-goals ("bespoke zero-knowledge circuits").

This ADR replaces the shielded-only architecture with a **transparent account ledger**: removing Orchard ordinary transfers, shielded coinbase, and Orchard pool accounting from experimental v1, committing transparent account state to the block header through `state_root`.

---

## 2. Decision

### 2.1 Scope of removal from v1
The following are removed from the OwnChain v1 consensus specification:
- **Orchard ordinary transfers:** The shielded `OrchardTransfer` transaction type is removed; ordinary transfers are transparent account transactions.
- **Shielded coinbase:** Shielded coinbase notes under zero-OVK are removed; block rewards and collected fees are paid to transparent addresses.
- **Pool accounting:** The Orchard V2 pool, `valueBalanceOrchard`, and pool balance upper bound tracking are removed; experimental v1 has no shielded pool.
- **Nullifier and anchor tracking:** Nullifier sets and commitment tree anchors are no longer required for ordinary transactions.

### 2.2 Transparent account model
Accounts are keyed by transparent 32-byte addresses derived from Ed25519 public keys (`BLAKE2b-256(UTF8("OwnChain/Address/v1") || ed25519_pk)`) and maintain:
- Balance (atoms, `u128_le`),
- Nonce (`u64_le`),
- Allowance and window limits,
- Freeze and recovery flags,
- 7-guardian configuration and per-transfer pending records (per ADR-002),
- 100-block coinbase maturity records (`coinbase_tranches`) tracking immature rewards until maturity.

### 2.3 `state_root` occupies header slot
The 170-byte block header is preserved. The 32-byte slot formerly occupied by `orchard_commitment_root` is assigned to `state_root`, which commits to the complete transparent account state (including balances, nonces, pending transfers, and coinbase maturity tranches) at the block boundary.

### 2.4 Domain-separated recursive-split Merkle tree
Both the transaction Merkle tree (`transaction_root`) and the account-state Merkle tree (`state_root`) use the RFC 6962-style recursive split with **no odd-leaf duplication**:
- `DOM_EMPTY`: `OwnChain/Merkle/Empty/v1`
- `DOM_LEAF`: `OwnChain/Merkle/Leaf/v1` (`0x00 || data`)
- `DOM_NODE`: `OwnChain/Merkle/Node/v1` (`0x01 || left || right`)
- Split point: $k = 1 \ll ((n - 1)\text{.bit\_length}() - 1)$ for $n \ge 2$.
- State tree leaves: accounts sorted strictly by `address` ascending (32 bytes raw unsigned comparison).

### 2.5 Genesis
Genesis `state_root` equals `EmptyRoot` (`BLAKE2b-256("OwnChain/Merkle/Empty/v1")`).

## 3. Alternatives

| Alternative | Assessment |
|---|---|
| **A. Status quo — keep shielded-only Orchard transfers** | Retains privacy but cannot support allowances, nonces, delayed withdrawals, or freeze/recovery without custom circuits (excluded). |
| **B. Dual ledger — shielded pool + transparent accounts** | Doubles consensus complexity (two state roots, value conversion). Overly complex for v1 experimental network. |
| **C. Transparent account ledger only (Accepted)** | Single state root, deterministic auditable balances, clean substrate for ADR-002 governance. |

---

## 4. Consequences & Risks

**Positive:**
- Enables transparent account balances, replay protection via nonces, spend allowances, delayed withdrawals, freeze/recovery, guardian quorums, and coinbase maturity enforcement.
- Deterministic, verifiable state commitment (`state_root`) verifiable by any node.
- Removes dependency on the pinned Orchard crate for ordinary payments and coinbase.

**Preserved Risks & Security Trade-offs:**
- **Loss of ordinary-transfer privacy:** Public ledger reveals transaction amounts, senders, recipients, and balances. Privacy against network or chain observers is forfeited for experimental v1.
- **State commitment overhead:** Maintaining the account state tree and recomputing `state_root` at block boundaries adds per-block execution cost.
- **Breaking consensus baseline:** Requires new genesis, header semantics, and independent test vectors.
- **Scope limitation:** Mainnet launch, exchange listing, and production PoW approval remain strictly out of scope.
