# ADR-004 — Shielded-First Hybrid Architecture

**Title:** Shielded-First Hybrid Architecture (Experimental-v1 baseline)  
**Identifier:** ADR-004  
**Status:** PROPOSED (Pending final owner review)  
**Date:** 2026-10-30  
**Author:** OwnChain consensus specification group  
**Depends on:** ADR-002 (Transparent account ledger and guardian governance), ADR-003 (Proof of work baseline)  
**Supersedes:** ADR-001 (Transparent-only transition)  

---

## 1. Context

OwnChain protocol v1 initially explored a shielded-only architecture, which was superseded by ADR-001 to establish a transparent-account ledger because account-level governance mechanics (spend allowances, sequential nonces, delayed withdrawals, account freeze/recovery, guardian quorums, and coinbase maturity tracking per ADR-002) could not be expressed within shielded notes without inventing bespoke zero-knowledge circuits. Custom circuits remain strictly excluded by OwnChain's core design non-goals.

However, transparent-only ledgers expose all transaction senders, recipients, and amounts publicly. By leveraging the established, upstream-reviewed Orchard V2 zero-knowledge circuit (`orchard = 0.16.0` with the post-NU6.2 `FixedPostNu6_2` circuit) without any custom ZK modifications, OwnChain can operate a **shielded-first hybrid blockchain**.

This ADR specifies the architecture, transaction registry, unified state commitment, cross-pool accounting rules, and global monetary conservation invariant uniting the Orchard V2 shielded pool and the Ed25519 transparent account ledger under a single native currency (OWN).

---

## 2. Decision

OwnChain experimental v1 adopts a **shielded-first hybrid architecture**:

1. **One native currency (OWN):** Both the shielded pool and the transparent ledger use the same native currency ($1\text{ OWN} = 100,000,000\text{ atoms}$).
2. **Shielded by default:** Wallets and user interfaces present shielded payments as the default transaction experience. Transparent transfers remain available as an explicit user choice.
3. **No custom zero-knowledge circuits:** All shielded functionality uses the pinned, upstream-verified Orchard V2 implementation (`orchard = 0.16.0`, `FixedPostNu6_2` circuit).
4. **Transparent ledger preservation:** Ed25519 accounts, sequential nonces, spend allowances, delayed withdrawals, and opt-in 7-guardian governance are preserved exactly as specified in ADR-002, with scope restricted to transparent accounts.
5. **Unified state commitment:** The fixed 170-byte block header carries a 32-byte composite `state_root` committing to transparent accounts, the Orchard commitment tree, the nullifier set, and the shielded pool balance.
6. **Global monetary conservation:** Strict value conservation enforced at all times: $T + S = I$, where cumulative issuance $I$ is strictly capped at 21,000,000 OWN.
7. **Cross-pool atomic fungibility:** Value moves between transparent accounts and shielded notes via atomic cross-pool transactions (Types 6 and 7).

## 3. Ledger Architecture

The OwnChain ledger operates two interoperable accounting systems within the same block:

### 3.1 Shielded Pool (Orchard V2)

- **Note commitments:** Shielded value is stored in note commitments added to a fixed depth-32 incremental Merkle tree.
- **Nullifier set:** Each spend reveals a unique 32-byte nullifier derived from the note's spending authorization key and position. Consumption of a nullifier permanently prevents double-spending.
- **Orchard bundle validation:** Bundles follow ZIP-225 Section 7 wire encoding and are verified using `FixedPostNu6_2` Halo2 proofs, RedPallas spend authorization signatures, and RedPallas binding signatures.
- **Stateless vs stateful boundary:**
  - Stateless validation verifies proofs, spend-auth signatures over action effects, and binding signatures.
  - Stateful consensus tracking maintains the historical anchor ring buffer (10-block window), the cumulative nullifier set, note commitment tree updates, and pool balance accounting.

### 3.2 Transparent Account Ledger

- **Authentication:** Ed25519 public keys ($32\text{ bytes}$) with signatures ($64\text{ bytes}$) over domain-separated preimages (`OwnChain/TxAuth/v1`).
- **Addresses:** Derived as $\text{BLAKE2b-256}(\text{UTF8("OwnChain/Address/v1")} \parallel ed25519\_public\_key[32])$.
- **State fields:** `balance` (atoms, `u128_le`), `nonce` (`u64_le`), spend allowances and active window tracking, freeze/recovery flags, 7-guardian configuration, pending transfer records, and coinbase maturity tranches.
- **Maturity rules:** Ordinary transfers mature in the next block. Coinbase rewards mature after 100 blocks.

## 4. Cross-Pool Transaction Rules

### 4.1 Value-Balance Sign Convention

Per upstream Orchard specification and verified integration tests (`tests/orchard_compat.rs`):
- `valueBalanceOrchard` is positive when value leaves the shielded pool.
- `valueBalanceOrchard` is negative when value enters the shielded pool.
- The consensus shielded pool balance delta is defined as:
  $$\Delta S = -\text{valueBalanceOrchard}$$

### 4.2 Cross-Pool Transitions

| Transition Type | Transparent Action | Shielded Action | Fee Source | Pool Balance Delta ($\Delta S$) | Invariant Check |
|---|---|---|---|---|---|
| **TransparentToShielded** (Type 6) | Sender debited: $-(A + F)$ | Notes created: $+A$ | Sender transparent | $+A$ | $\Delta T + \Delta S + F_{miner} = 0$ |
| **ShieldedToTransparent** (Type 7) | Recipient credited: $+A$ | Note spent: $-(A + F)$ | Shielded spend | $-(A + F)$ | $\Delta T + \Delta S + F_{miner} = 0$ |
| **ShieldedTransfer** (Type 5) | None | Notes spent & created: net $-F$ | Shielded spend | $-F$ | $\Delta S + F_{miner} = 0$ |
| **TransparentTransfer** (Type 1) | Sender $- (A+F)$, Recipient $+A$ | None | Sender transparent | $0$ | $\Delta T + F_{miner} = 0$ |

All cross-pool transactions execute atomically. If any condition fails, the entire transaction is rejected and zero state changes are committed.

### 4.3 Orchard Anchor Policy

To bound validation complexity and ensure fork-choice consistency:
1. **10-block ancestor window:** A shielded spend bundle may reference the Orchard commitment tree root from any of the 10 immediate ancestor blocks ($[h-10, h-1]$).
2. **No intra-block anchors:** A transaction cannot reference an Orchard root produced by an earlier transaction in the same candidate block.
3. **Selected chain validation:** The anchor must exist on the active chain branch.
4. **Reorganization invalidation:** Any transaction whose anchor is reorged out becomes invalid unless re-anchored.
5. **Nullifier persistence:** Duplicate nullifiers remain invalid across forks and anchors.

## 5. Value Conservation and Monetary Rules

### 5.1 Global Conservation Invariant

At the end of every block:
$$T + S = I$$

Where:
- $T = \sum_{a \in \text{Accounts}} a.balance$ (sum of all transparent account balances).
- $S$ = cumulative consensus shielded pool balance (atoms).
- $I$ = cumulative actual OWN issuance (atoms).

### 5.2 Pending Principal and Spendable Balance

Pending transfer principal remains included in the sender's total `balance` but is subtracted from `spendable_balance`. It is **not** counted twice in the global invariant:
$$\text{spendable\_balance}(h) = balance - \sum_{t \in \text{coinbase\_tranches}, t.unlock\_height > h} t.amount - \sum_{p \in \text{pending\_transfers}} p.amount$$

All arithmetic is checked unsigned 128-bit integers; underflow or overflow is an immediate consensus violation.

### 5.3 Coinbase and Subsidy Rules

- **Starting subsidy:** 10 OWN ($1,000,000,000\text{ atoms}$).
- **Halving interval:** 1,050,000 blocks.
- **Subsidy formula:** $\text{subsidy}(h) = 1,000,000,000 \gg \lfloor (h - 1) / 1,050,000 \rfloor$ atoms.
- **Hard cap:** 21,000,000 OWN ($2,100,000,000,000,000\text{ atoms}$).
- **Subsidy exhaustion:** At Era 30 (height 31,500,001), scheduled subsidy drops to 0 atoms. Miner payouts consist exclusively of collected transaction fees.
- **Coinbase payout:**
  $$\text{coinbase\_payout} = \sum \text{fees} + \text{actual\_subsidy\_claimed}$$
  Where $0 \le \text{actual\_subsidy\_claimed} \le \text{scheduled\_subsidy}(h)$ and $I + \text{actual\_subsidy\_claimed} \le 21,000,000\text{ OWN}$.
  Unclaimed subsidy is permanently unissued.

## 6. Authoritative Transaction Registry

OwnChain defines exactly eight transaction types (0 through 7). The outer envelope is identical for all types:
$$\text{tx\_type}:\text{u8} \parallel \text{tx\_version}:\text{u16\_le} \parallel \text{chain\_id}:[u8; 32]$$

| Type | Name | Purpose | Canonical Size | Authorization | `valueBalanceOrchard` |
|---|---|---|---|---|---|
| **0** | **Coinbase** | Miner subsidy + fees payout | 83 bytes | Valid block proof of work | $v = 0$ |
| **1** | **TransparentTransfer** | Transparent account-to-account | 195 bytes | Sender Ed25519 signature | $v = 0$ |
| **2** | **ConfigureGuardians** | Opt-in / reconfigure guardians | Variable | Owner Ed25519 (+ 4-of-7 if reconfiguring) | $v = 0$ |
| **3** | **GuardianAction** | Freeze, unfreeze, recovery, delays | Variable | 3-of-7 or 4-of-7 guardian quorum | $v = 0$ |
| **4** | **CancelPendingTransfer** | Cancel delayed transfer | Variable | Sender Ed25519 + 4-of-7 guardian quorum | $v = 0$ |
| **5** | **ShieldedTransfer** | Pure Orchard shielded transfer | Variable | Orchard proofs, spend-auth & binding sigs | $v = +fee\_atoms$ |
| **6** | **TransparentToShielded** | Transparent funds enter Orchard | Variable | Sender Ed25519 (+ 4-of-7 if protected) + Orchard | $v = -shielded\_amount$ |
| **7** | **ShieldedToTransparent** | Orchard funds exit to transparent | Variable | Orchard proofs, spend-auth & binding sigs | $v = +(release\_amount + fee\_atoms)$ |

*Note: Coinbase maturity is an automatic state transition at block boundaries; there is no user-submitted `CoinbaseMaturityTransfer` transaction.*

### Minimum Fee Formula
For every transaction:
$$\text{min\_fee} = \max(1, 100 \times \text{canonical\_signed\_size\_bytes})\text{ atoms}$$

### Canonical Transaction Identifier
$$\text{tx\_id} = \text{BLAKE2b-256}(\text{UTF8("OwnChain/Tx/v1")} \parallel \text{canonical\_signed\_tx\_bytes})$$

## 7. Unified State Commitment

The block header remains exactly **170 bytes**. The 32-byte slot at offset 106 (`state_root`) holds the domain-separated composite state root:

```
state_root = BLAKE2b-256(
    UTF8("OwnChain/CompositeStateRoot/v1") ||
    transparent_account_state_root[32]    ||
    orchard_commitment_tree_root[32]      ||
    nullifier_state_root[32]              ||
    shielded_pool_balance_commitment[32]
)
```

Where:
1. `DOM_COMPOSITE = UTF8("OwnChain/CompositeStateRoot/v1")` is **exactly 30 raw UTF-8 bytes** (no `0x0e` prefix).
2. `transparent_account_state_root`: Recursive-split Merkle root over all accounts sorted by raw 32-byte address ascending.
3. `orchard_commitment_tree_root`: Root of the depth-32 Orchard note commitment tree (pinned empty root `ae2935f1dfd8a24aed7c70df7de3a668eb7a49b1319880dde2bbd9031ae5d82f` at genesis).
4. `nullifier_state_root`: Recursive-split Merkle root over the set of all consumed nullifiers sorted lexicographically ascending. Empty root is $\text{BLAKE2b-256}(\text{UTF8("OwnChain/Nullifier/Empty/v1")})$.
5. `shielded_pool_balance_commitment`: $\text{BLAKE2b-256}(\text{UTF8("OwnChain/PoolBalance/v1")} \parallel \text{shielded\_pool\_balance}:\text{u128\_le})$.

### Genesis Composite State Root
Genesis calculates all four component commitments:
- $T_{\text{empty}} = \text{BLAKE2b-256}(\text{UTF8("OwnChain/Merkle/Empty/v1")})$
- $O_{\text{empty}} = \text{ORCHARD\_EMPTY\_ROOT}$
- $N_{\text{empty}} = \text{BLAKE2b-256}(\text{UTF8("OwnChain/Nullifier/Empty/v1")})$
- $S_{\text{empty}} = \text{BLAKE2b-256}(\text{UTF8("OwnChain/PoolBalance/v1")} \parallel 0:\text{u128\_le})$

And derives `genesis_state_root` via the standard composite formula.

## 8. Guardian Scope and Quorum Matrix

Guardian protection is **strictly opt-in and account-specific**:
- Guardians govern only transparent accounts that explicitly register them.
- Guardians have **no authority over shielded notes**. Once funds enter the shielded pool, they are governed entirely by Orchard spending keys.
- Shielded notes must never be advertised as guardian-protected.

### Authoritative Quorum Matrix (7 Distinct Ed25519 Keys)

| Action | Quorum | Purpose / Justification |
|---|---:|---|
| **Strengthen protections** | **3-of-7** | Lower threshold to tighten security |
| **Increase delays** | **3-of-7** | Increase new-recipient or withdrawal delay |
| **Tighten allowance** | **3-of-7** | Lower spend limit or lengthen window duration |
| **Weaken protections** | **4-of-7** | Strict majority to reduce protections |
| **Decrease delays** | **4-of-7** | Decrease configured delays |
| **Increase allowance** | **4-of-7** | Increase spend limit or shorten window duration |
| **Freeze account** | **4-of-7** | Halt outgoing transfers from compromised account |
| **Unfreeze account** | **4-of-7** | Restore account operation after review |
| **Emergency recovery** | **4-of-7** | Sweep spendable balance to pre-registered recovery key |
| **Replace guardian set** | **4-of-7** | Update 7-guardian public key list |
| **Replace recovery key** | **4-of-7** | Update registered emergency recovery key |
| **Cancel pending transfer** | **4-of-7** | Revoke in-flight transfer before release height |
| **Cross-pool shielding** | **4-of-7** | Authorize funds leaving protected account to Orchard |

## 9. Resolution of Consensus Specifications (Formerly Blockers)

All five consensus blockers identified during initial drafting are formally resolved:

1. **Nullifier-State Commitment:** Specified as an authenticated, sorted recursive-split Merkle tree using domain separators `OwnChain/Nullifier/Empty/v1`, `Leaf/v1`, and `Node/v1`. This avoids hash-chain length extension issues and supports verifiable inclusion proofs.
2. **Shielded Pool Balance Commitment:** Specified as $\text{BLAKE2b-256}(\text{UTF8("OwnChain/PoolBalance/v1")} \parallel \text{balance}:\text{u128\_le})$. Commits to public cumulative atoms only; no age-weighting or hidden note heuristics.
3. **Cross-Pool Value Conservation:** Enforced by the global invariant $T + S = I$ with checked integer arithmetic.
4. **Atomic Rejection Conditions:** Evaluated as an atomic transaction bundle. If signature, nonce, balance, proof, anchor, or nullifier verification fails, state reverts completely.
5. **Composite State Root Hash Function:** Standardized on unkeyed BLAKE2b-256 with 30-byte domain separator `OwnChain/CompositeStateRoot/v1`.

## 11. Consequences and Risks

- **Positive:** Full transaction privacy by default; transparent auditing when chosen; zero custom ZK circuits; mathematical value conservation; robust opt-in guardian safety.
- **Risks:** Cross-pool graph analysis (users must follow shielding best practices); dual-state tree maintenance overhead; client wallet complexity managing both transparent and Orchard keys.
