# ADR-005 — Embedded Persistent Storage Selection for Node Runtime

**Title:** Embedded Persistent Storage Selection for Node Runtime  
**Identifier:** ADR-005  
**Status:** ACCEPTED  
**Date:** 2026-11-06  
**Author:** OwnChain consensus and runtime architecture group  
**Depends on:** ADR-002, ADR-004, docs/protocol-v1.md §6, §8  

---

## 1. Context

Milestones M1-A through M1-H established the in-memory consensus baseline for OwnChain v1, including the transparent account ledger, 7-guardian governance, Orchard V2 shielded-first hybrid ledger, and RandomX proof of work. However, the existing implementation evaluated state transitions purely in-memory: terminating the node process resulted in total loss of accepted chain history and state.

Milestone M1-I requires persistent block and chain storage to allow independent node processes to:
1. Persist canonical block bytes using `Block::to_bytes()`.
2. Index blocks by block ID (`Hash`).
3. Maintain an active chain index mapping block height to active block ID.
4. Persist network chain ID, tip block ID, active tip height, cumulative work, and schema version.
5. Retain validated side-branch blocks needed for chain reorganizations.
6. Guarantee crash-consistency: atomic commits such that partial or failed writes never corrupt active chain state.
7. Support deterministic startup state reconstruction via sequential re-application of canonical blocks against consensus rules.

---

## 2. Options Considered

### Option A: `redb` (Pure-Rust Embedded Key-Value Database)
- **Architecture:** ACID key-value store written entirely in Rust, using copy-on-write B-trees with multi-version concurrency control (MVCC) and two-phase commit.
- **Portability:** 100% safe Rust in its public API, zero native C/C++ dependencies or build-script requirements. Cross-compiles trivially across Windows, Linux, and macOS.
- **Crash Safety:** Strong transactional ACID guarantees. Write transactions commit atomically; uncommitted or interrupted transactions roll back cleanly on restart.
- **Maintenance:** Actively maintained with mature 2.x releases.

### Option B: `rocksdb` (Rust bindings to C++ RocksDB)
- **Architecture:** Log-Structured Merge-tree (LSM) embedded database.
- **Disadvantages:** Requires a C++ toolchain and CMake build integration; compilation times are heavy; significant operational complexity and memory footprint tuning.

### Option C: `heed` (LMDB Rust wrapper)
- **Architecture:** B-tree embedded database based on LMDB using memory-mapped files.
- **Disadvantages:** Relies on C LMDB; on Windows platforms, LMDB memory mapping encounters known file-locking, resize, and crash-recovery caveats.

### Option D: `sled` (Pure-Rust embedded database)
- **Architecture:** Lock-free Bw-tree architecture.
- **Disadvantages:** Development stalled in alpha/beta status; historical reports of data corruption during unclean shutdowns.

---

## 3. Decision

We choose **`redb`** as the persistent storage engine for the OwnChain node runtime.

Key design attributes:
1. **Schema Versioning:** An explicit database schema version (`DATABASE_SCHEMA_VERSION = 1`) and network `chain_id` are committed to a dedicated metadata table during initialization. Startup verifies compatibility and rejects mismatched databases.
2. **Tables:**
   - `blocks`: `block_id: [u8; 32] -> canonical_block_bytes: &[u8]` (stores both canonical and side-branch blocks).
   - `height_to_block_id`: `height: u64 -> block_id: [u8; 32]` (canonical active chain index).
   - `block_metadata`: `block_id: [u8; 32] -> metadata: &[u8]` (parent ID, height, cumulative work).
   - `chain_metadata`: `key: &str -> value: &[u8]` (tip block ID, tip height, cumulative work, network chain ID, schema version).
3. **Atomic Multi-Table Transactions:** Block persistence, active chain index advancement, tip updates, and metadata updates commit inside a single `redb::WriteTransaction`.
4. **Deterministic Reconstruction:** Node startup initializes a fresh `ChainState::from_genesis(&genesis)` and replays the stored canonical blocks in height order through `apply_block`, verifying the reconstructed tip and composite state root against persisted metadata.
